# Sessions

## 2026-07-02 — BS4 decompose fix deployed and verified; MALLOC_ARENA_MAX=2 added
Applied the pending `soup.decompose()` fix (`try/finally` in both `RargbCrawler.crawl()` and `ImdbCrawler.crawl()`), rebuilt/redeployed, and verified it live: memory grew only while the ~3,000-message `crawl_imdb` backlog drained (peak 4.06 GiB) and stayed flat across 6 minutes of idle sampling — no active leak. The residual ~4 GiB RSS was diagnosed as glibc arena retention (freed heap not returned to the OS across 7 threads), so `MALLOC_ARENA_MAX=2` was added to `docker-compose.yml` and the container recreated (fresh baseline 1.04 GiB); the next backlog drain is the real test of the peak.

## 2026-07-02 — OOM investigation: browser leak fix deployed, BS4 cycle leak found (fix pending)
Diagnosed two distinct OOM causes from `app.log` and live container inspection: (1) `RargbCrawler`'s Chromium process was never closed per `crawl_rargb` trigger — fixed with `RargbCrawler.close()` / `BrowserDriver.close()` / `try/finally` in `service.py`, rebuilt and redeployed, confirmed zero leaked processes after 3 test triggers. (2) A second, unfixed leak: `ImdbCrawler`/`RargbCrawler` BeautifulSoup trees hold parent/child reference cycles that only cyclic GC reclaims, and under back-to-back IMDb crawling of a large backlog the app process grew to ~5GB RSS and drove the host to 141MB free / swap exhausted; mitigated by stopping the `myrargb` container (no data lost, Kafka offsets commit per-message). Planned but **not yet applied**: `soup.decompose()` after data extraction in both crawlers' `crawl()` methods to sever cycles proactively instead of relying on GC catching up. Also surfaced a separate, unrelated backlog gap (movies inserted with no `predict`/`crawl_imdb` Kafka message produced, likely from a transient Kafka outage) — backfilled manually via `/produce/predict` and `/produce/imdb`; a periodic self-healing backfill thread was proposed but not built.
